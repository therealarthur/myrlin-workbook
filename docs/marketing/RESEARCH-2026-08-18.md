## 3. Measured on this machine

These are the load-bearing numbers. They were produced here, today, rather than quoted.

### 3.1 The encoder situation is already solved

`ffmpeg-static` 5.3.0 resolves to `ffmpeg 6.1.1-essentials_build-www.gyan.dev`, configured with `--enable-libwebp --enable-libx264 --enable-libx265 --enable-libaom`. Both `libwebp_anim` and `libwebp` encoders are present, as are `palettegen`, `paletteuse`, `xfade` and `reverse`. `libsvtav1` is absent, which rules out SVT-AV1 without a different build.

`sharp` 0.34.5 bundles libvips with **libwebp 1.6.0** and round-trips animated WebP correctly: a 72-frame clip resized by width came back as 72 pages with `loop: 0` intact.

### 3.2 Animated WebP versus GIF, on this project's real assets

Converting the three GIFs currently committed in `docs/images/`, at 900px wide and 10 fps:

| Asset | GIF today | Animated WebP | Reduction |
| --- | --- | --- | --- |
| `hero-demo.gif` | 7,372 KB | 868 KB | 8.5x |
| `workspace-docs.gif` | 3,840 KB | 412 KB | 9.3x |
| `theme-switching.gif` | 2,072 KB | 208 KB | 10.0x |
| **Total** | **13,284 KB** | **1,488 KB** | **8.9x** |

Converting the existing GIFs alone removes roughly **11.8 MB** from the repository. That is the single cheapest win available and needs no new capture.

A controlled synthetic comparison at 900px and 24 fps gave animated WebP 844 KB against GIF 2,836 KB, a 3.4x gap on high-entropy content. Real UI content compresses far better, which is why the table above shows 8x to 10x.

### 3.3 Frame rate ceilings, measured

| Capture method | Result | Verdict |
| --- | --- | --- |
| Playwright 1.58 `recordVideo` | **25.0 fps** exactly (97 frames / 3.88 s), VP8 in WebM, 1440x900 | Hard ceiling; not smooth enough for a hero |
| Raw CDP `Page.startScreencast`, `everyNthFrame: 1` | **59.2 fps** (178 frames / 3.01 s), PNG frames | Smooth, but low level |
| Playwright 1.62 `page.screencast` with `onFrame` | **45.9 fps** (294 frames / 6.41 s) with overlays and a click, JPEG frames plus a WebM written at `path` | The recommended path |

Encoding the 59 fps CDP frames produced a true 60 fps H.264 file (`60 fps, 60 tbr`) with faststart. So 60 fps output is achievable; `recordVideo` simply cannot reach it.

**Screencast frames are 1x CSS pixels, always.** With `deviceScaleFactor: 2` and `maxWidth`/`maxHeight` set to 2880x1800, screencast frames still arrived at 1440x900, while `page.screenshot()` on the same context produced 2880x1800. So: screencast for video, `page.screenshot()` for retina stills. This is not documented and was flagged UNVERIFIED by research; it is now settled.

### 3.4 Playwright 1.62 `page.screencast` exists and works

Verified in the shipped `playwright-core@1.62.1` type definitions and then executed on this machine:

```
start(options?: { onFrame?, path?, size?, quality?, annotate? })
showActions({ cursor: "none"|"pointer", duration, fontSize, position })
showChapter(title, { description, duration })
showOverlay(html, { duration })
hideActions() / showOverlays() / hideOverlays() / stop()
```

`showOverlay()` accepts arbitrary HTML. That solves feature-callout overlays natively, without compositing in Remotion, for the common case.

### 3.5 The brand-font trap, reproduced

Neither Plus Jakarta Sans nor JetBrains Mono is installed in the Windows font store, and the app loads both from the Google Fonts CDN. Rendering an SVG wordmark through `sharp` therefore **silently substituted a generic monospace face for both fonts**, produced no warning, and exited successfully.

This directly invalidates copying the competitor's `scripts/make-social.mjs` approach onto this machine. Their script names Helvetica Neue, which exists on macOS; ours would ship an off-brand OG image with no error. Use Playwright HTML to PNG, or satori with explicit font buffers.

### 3.6 The competitor's numbers, read off their actual files

Downloading nodeterm's committed assets and inspecting them:

| File | Dimensions | Frames | Loop | Frame delay | Size |
| --- | --- | --- | --- | --- | --- |
| `hero-tour.webp` | 880x495 | 300 | infinite | 100 ms | 2,734 KB |
| `canvas-tour.webp` | 800x450 | 140 | infinite | 100 ms | 1,188 KB |
| `kanban-launch.webp` | 800x450 | 150 | infinite | 100 ms | 984 KB |

The calibration that matters: **they run at 10 fps, not 30 or 60**. A 30-second hero at 10 fps and 880px lands at 2.7 MB. High frame rate belongs in the MP4 click-through, not in the inline WebP.

### 3.7 GitHub really does render animated WebP in a README

This was flagged UNVERIFIED by two independent research passes, because GitHub's docs still omit WebP and the 2025-08-28 changelog mentions only comment boxes and blob views. It is now settled by direct observation: fetching the rendered HTML of `https://github.com/eneskirca/nodeterm` returns

```html
<img src="/eneskirca/nodeterm/raw/main/docs/assets/hero-tour.webp" alt="..." width="900" style="max-width: 100%;">
```

a normal inline `<img>` against the repo `raw` path, not a "View raw" link and not a camo-proxied external URL. Combined with 3.6, which proves those files carry 300 animated frames, animated WebP in a README is confirmed working on a live public repository.

**One caveat that survives:** a user in GitHub community discussion 171343 reports WebP served from GitHub asset endpoints returning 404 when embedded **externally**, for example on npm. See the npm rendering risk in area 6 and in the risks section.

### 3.8 The animated logo is not a vector, which blocks the icon track

Parsing `docs/images/logo-animated.svg` directly:

```
bytes: 69854          viewBox: 0 0 250 210
<path> elements: 0
<image> elements: 1
embedded raster: PNG, 51714 bytes decoded, 238x192
```

It is a CSS animation wrapper around a base64-encoded **238x192 PNG**. There is no vector artwork in it at all. Consequences, all of which change earlier assumptions:

- Any 512x512 app icon derived from it is a **2.7x upscale of a 238px raster** and will be visibly soft.
- An `icon.svg` favicon built from this file would be a 70 KB SVG containing a PNG. It buys none of the benefits of an SVG favicon: no crispness at arbitrary size, and no `@media (prefers-color-scheme: dark)` restyling, because there are no paths to restyle.
- The viewBox is 250x210, not square, so every square icon needs `fit: 'contain'` padding.
- The Remotion logo animation cannot be done by porting SVG paths to a frame-driven component, because there are none.

**A genuine square vector master is a prerequisite for the entire logo and icon track.** Everything else in the icon plan is ready to run the moment one exists.

### 3.9 The installed sharp carries a high severity advisory

`npm audit` on this tree reports 5 vulnerabilities, 3 high and 2 moderate. The one that matters for this pipeline:

```
sharp  [high]  range=<0.35.0  direct dep
  via: sharp inherited vulnerabilities in libvips:
       CVE-2026-33327, CVE-2026-33328, CVE-2026-35590, CVE-2026-35591
  fixAvailable: sharp 0.35.3  (isSemVerMajor: true)
```

`package.json` declares `"sharp": "^0.34.5"`. A caret on a `0.x` version pins the minor, so `npm update` will never reach 0.35.x and `npm audit fix` will not apply it either, because the fix is flagged as a semver-major change. It stays exposed until someone bumps it explicitly.

Severity in context: sharp is a devDependency here and these are libvips image-decoding CVEs, so the realistic exposure is build-time processing of untrusted image input rather than anything reachable by a user of the app. Given this pipeline will start feeding sharp a lot of generated media, bump it:

```powershell
npm i -D sharp@^0.35.3
```

Nothing in the recommended pipeline constrains sharp to 0.34. Note for the migration: 0.35.0 requires Node 20.9.0 or newer, removes `failOnError` and `paletteBitDepth`, and renames `format.jp2k` to `format.jp2`.

This also settles an icon dependency question. `favicons@7.3.1` requires `sharp ^0.35.3` while `@realfavicongenerator/image-adapter-node@0.8.4` pins `sharp ^0.34.5`, the vulnerable line; either would install a **second duplicate sharp native binary** alongside the project's own. That reinforces the pick of sharp plus `png-to-ico` and nothing else.

The other four findings are outside this pipeline but worth passing on: `blessed-contrib` (high, direct, via `lodash` and `map-canvas`), `lodash` (high, transitive), `map-canvas` and `xml2js` (moderate, transitive). Those belong to the TUI dependency chain, not to media work.

### Why `page.screencast` wins for this project

It is the only option that gives an exact viewport with no window positioning, runs headless (so it does not violate the project's Windows process-safety rule), needs no new dependency beyond a version bump, and provides the annotation layer that is otherwise the hardest part to build. MEASURED HERE at 45.9 fps with overlays active, against 25.0 fps for `recordVideo`.

`showChapter()` gives titled chapter cards, `showActions({ cursor: 'pointer' })` draws a cursor and highlights the element being acted on, and `showOverlay(html)` accepts arbitrary HTML for callouts. Between them, most feature-callout work never needs a compositor.

**Do not use OS-level capture.** Windows `gdigrab` is a GDI BitBlt loop that community reports say does not reach a true 60 fps, and it captures a screen region rather than a viewport, so every notification and taskbar risks landing in frame. `ddagrab` plus `h264_nvenc` is the modern Windows answer but needs a headful browser plus a GPU encoder running alongside agent work.

**Reuse the harness that already exists.** `test/browser/notion-shell.spec.js` already spawns the server on an ephemeral port, explicitly refuses to touch port 3456 because that serves the live checkout, seeds deterministic fixtures with frozen timestamps, and drives a capture matrix at 1280x800 and 390x844 with `deviceScaleFactor: 1`. The media harness should be a sibling of that file, not a new invention.

### The Remotion license, stated plainly

Verified at https://github.com/remotion-dev/remotion/blob/main/LICENSE.md and https://www.remotion.pro/license. The Free License covers an individual, a non-profit, or a for-profit organization with **up to 3 employees**. A company of 4 or more needs a paid Company License, from $25 per month per seat or a $100 per month minimum on the per-render plan. Remotion's own FAQ says: "Remotion is source-available software, but it is not open-source software."

A solo maintainer qualifies for free commercial use today. The hygiene rule that follows: **keep Remotion out of the published npm package's dependency tree.** Put it in a `media/` folder excluded via `files` or `.npmignore`, so a downstream company consuming an AGPL-3.0 package never inherits a Remotion licensing obligation.

### Remotion has official Claude Code skills now, and its MCP is deprecated

- Skills: `npx remotion skills add` installs 12 skills into `.agents/skills` with a `.claude/skills` symlink. https://www.remotion.dev/docs/cli/skills
- Plugin: `claude plugin marketplace add remotion-dev/claude-code-plugin`. https://www.remotion.dev/docs/ai/claude-code-plugin
- MCP: deprecated. https://www.remotion.dev/docs/ai/mcp states "The Remotion MCP is deprecated" and that the hosted MCP shuts down no earlier than 2026-08-31.

Windows x64 is supported; `@remotion/compositor-win32-x64-msvc` 4.0.512 exists and Chrome Headless Shell downloads automatically. Windows ARM64 has no compositor binary.

Remotion emits GIF natively via `--codec=gif`, `--every-nth-frame` and `--number-of-gif-loops`, but **cannot emit animated WebP**. That last step is one ffmpeg call.

### Picks per deliverable

| Deliverable | Pick | Reasoning |
| --- | --- | --- |
| Logo animation | **Blocked.** Redraw the mark as real vector art first, then Remotion for the rendered file and Anime.js 4.5.0 for the in-app version | MEASURED HERE, section 3.8: `logo-animated.svg` contains **zero `<path>` elements** and one `<image>` holding a 238x192 base64 PNG. There is nothing to animate frame by frame and nothing to restyle for dark mode. Its CSS animation is also wall-clock, so it would not render deterministically even if there were. Anime.js is true MIT and safe inside the AGPL codebase |
| Kinetic typography verticals | Remotion at 1080x1920 | One `Sequence` per line with spring entrances; the `remotion-markup` skill covers this |
| Feature callout overlays | **Playwright `showOverlay()` first**, Remotion `OffthreadVideo` when the callout must be frame-exact | Use the simplest thing that works and escalate only when needed |
| Stop-motion / animotion | Remotion with held frames plus `--every-nth-frame` | Gives the chunky cadence for free |

### One trap worth stating

**Do not drop Rough Notation, raw GSAP, Anime.js or Motion timelines into a Remotion composition and let them auto-play.** They are all wall-clock engines. Under frame-by-frame rendering the browser clock does not advance as they expect, so annotations render either fully drawn or not at all, inconsistently. Drive them from `useCurrentFrame()` instead, or generate the geometry and animate the dash offset yourself.

### The honest verdict

**Do not use AI to render text, and do not use AI video for anything showing the product.**

On text: DeepMind's own claim for its best model is "the lowest error rates (mostly under 10%)" on single-line text. An ad still with a headline, a subhead and a wordmark is three or more dice rolls per render, and the output cannot use the real Plus Jakarta Sans or JetBrains Mono. Compose ad-still text in HTML and screenshot it. That gives exact kerning, real brand fonts, versionable source, instant re-renders at every size, and zero cost.

On video: no model can generate this actual UI. Any attempt produces a plausible fake interface, which for a developer audience on X and Reddit is actively damaging. Real screen capture is strictly better and is already free.

Where AI genuinely earns a place, narrowly: abstract background plates composited under CSS, one to two second logo stingers, and mood cutaways. Even there, an animated CSS or WebGL gradient is free, deterministic, on-brand and artifact-free.

**Privacy note:** Gemini's free tier trains on submitted content; the paid tier does not. Use a paid key for anything brand-related. All Gemini images carry a SynthID watermark.

## 7. Area 4: encoding pipeline

### The single most important gotcha

**`-loop` is a WebP muxer option and its default is 1, meaning play once and stop.** It is not documented on the ffmpeg libwebp encoder page.

```
-loop <int>  E.......... Number of times to loop the output: 0 - infinite loop (default 1)
```

Byte-identical payloads, different ANIM chunk: without the flag the file reports `loopCount 1`; with `-loop 0` it reports infinite. This is the real cause of most reports that a WebP will not loop. Note that **GIF is the opposite**: its muxer defaults to `-loop 0`, infinite.

### Other verified corrections

- `-compression_level` is a generic codec option, not a libwebp private one. It works, and 6 is worth setting: measured 90,910 bytes at level 6 against 130,700 at level 0.
- `-preset` takes named strings. On text-heavy UI content `-preset text` beat `picture`, 84,932 against 90,850 bytes. Try both, keep the smaller.
- **`-lossless 1` is a size trap:** 10,772,346 bytes against 1,555,066 lossy on the same clip, 6.9x larger.
- **Always pass `-pix_fmt yuv420p`.** From RGB PNG input with no flag, ffmpeg silently picks `yuv444p`, which is H.264 High 4:4:4 Predictive; it plays in Chrome and fails in QuickTime and Safari.
- **`scale=-1` fails on odd dimensions.** Always use `scale=W:-2`.
- `-movflags +faststart` verified by atom order: `ftyp,moov,free,mdat` with the flag, `ftyp,free,mdat,moov` without.
- CRF sweep at 1440x900, preset slow: crf 23 gave 4.2 MB, crf 28 gave 2.1 MB, **crf 30 gave 1.6 MB**, crf 32 gave 1.3 MB. crf 30 matches the competitor's setting.
- **Animated AVIF: do not use.** GitHub does not support AVIF; community discussion 138164 has been open since 2024-09-09 with no changelog, and caniuse flags a Firefox bug for image sequences. It would render as a broken image.
- **Do not use x265 or AV1 for delivery.** GitHub explicitly recommends H.264 for browser compatibility, and this ffmpeg build has no `libsvtav1` anyway.

### sharp's animated-WebP filmstrip trap

sharp represents an animation as one tall vertical strip. For a 96-frame clip, `metadata().height` returns **66048**, not the frame height. Use `pageHeight` for the real height, and **only ever resize by width**. Resizing by height squashes every frame into a single strip. sharp's `loop` defaults to 0, the opposite of ffmpeg, which makes sharp the safer tool for the final pass.

### The encode ladder

```bash
FF="$(node -p "require('ffmpeg-static')")"
```

**(a) Inline animated WebP for the README**, target 250 to 600 KB:
```bash
"$FF" -y -i capture.webm \
  -vf "fps=12,scale=1100:-2:flags=lanczos" \
  -c:v libwebp_anim -preset picture -quality 70 -compression_level 6 -loop 0 -an \
  docs/media/feature-01.webp
```
If over budget, drop to `fps=10` or `scale=900:-2` before touching quality. Frame rate and width are the levers, not quality.

**(b) MP4 click-through**, target 1 to 3 MB, attached to a GitHub Release rather than committed:
```bash
"$FF" -y -i capture.webm -vf "scale=1440:-2:flags=lanczos" \
  -c:v libx264 -profile:v high -level 4.0 -preset slow -crf 30 \
  -pix_fmt yuv420p -movflags +faststart -an dist/tour.mp4
```

**(c) Poster frame**, under 60 KB. Put `-ss` before `-i` for a fast seek, and use the still encoder:
```bash
"$FF" -y -ss 2.5 -i capture.webm -frames:v 1 \
  -vf "scale=1100:-2:flags=lanczos" \
  -c:v libwebp -quality 82 -compression_level 6 docs/media/tour-poster.webp
```

**(d) Vertical 1080x1920 for X and Reddit**, with a silent AAC track because some players misbehave with no audio stream:
```bash
"$FF" -y -i capture.webm -f lavfi -i anullsrc=channel_layout=stereo:sample_rate=44100 \
  -filter_complex \
  "[0:v]scale=1080:-2:flags=lanczos,setsar=1[fg];\
   [0:v]scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920,boxblur=40:4,setsar=1[bg];\
   [bg][fg]overlay=(W-w)/2:(H-h)/2,format=yuv420p[v]" \
  -map "[v]" -map 1:a -c:v libx264 -preset slow -crf 26 -pix_fmt yuv420p -r 30 \
  -c:a aac -b:a 128k -shortest -movflags +faststart dist/tour-vertical.mp4
```

**Seamless looping.** Cheapest is designing the capture so the first and last frame match, which costs nothing. Boomerang via `reverse` plus `concat`, with `trim=start_frame=1` to drop the duplicated pivot frame, doubles file size exactly. An `xfade` of the tail into the head costs almost nothing and can even shrink the file.

### Verify before publishing

A WebP that does not loop looks fine locally and broken on GitHub. Check every file:

```js
// docs/marketing/webpinfo.js
const fs = require('fs');
for (const f of process.argv.slice(2)) {
  const b = fs.readFileSync(f); let o = 12, frames = 0, loop = null, anim = false;
```

### Why Playwright wins here, and when satori is still right

Playwright already exists in this project, already renders the exact design system, and needs no font wrangling at all because the page loads Google Fonts the same way the app does. One HTML template with CSS custom properties, one loop over an artboard manifest, and every asset comes out consistent by construction. It also gives you the one thing satori cannot: a **real screenshot of the real app** composited inside the artboard, which is the whole point of an ad still.

The exact API for pixel-exact output:

```js
const ctx = await browser.newContext({
  viewport: { width: 1200, height: 630 },
  deviceScaleFactor: 2,            // emits 2400x1260
});
const page = await ctx.newPage();
await page.goto(`file://${templatePath}?variant=og`);
await page.evaluate(() => document.fonts.ready);   // do not screenshot before fonts settle
await page.screenshot({ path: 'og.png' });          // or element.screenshot() for one artboard
```

Two things that matter and are easy to miss. Await `document.fonts.ready` or the first render can capture fallback glyphs, which reintroduces exactly the failure this pick was chosen to avoid. And `deviceScaleFactor: 2` on a 1200x630 artboard yields 2400x1260, which is over the 2000px agent-review limit, so downscale before any agent looks at it.

**Use satori instead when** you want OG images generated on demand at request time from a deployed function, for example per-page cards on the landing site. It is far lighter than launching Chromium. For a fixed set of brand assets built once per release, Playwright is simpler and higher fidelity. If you do go satori, supply the font as a buffer:

```js
const jakarta = fs.readFileSync('docs/marketing/fonts/PlusJakartaSans-Bold.ttf');
const svg = await satori(markup, { width: 1200, height: 630, fonts: [{ name: 'Plus Jakarta Sans', data: jakarta, weight: 700, style: 'normal' }] });
```

### If you must use sharp plus SVG

Three workarounds exist, in descending reliability:

1. **Embed the font in the SVG as a base64 data URI** inside an `@font-face` in a `<style>` block. Self-contained and portable.
2. **Convert the text to paths** ahead of time, so no font resolution happens at render. Most reliable, but the text is no longer editable.
3. Install the fonts system-wide. Works, but makes the build machine-dependent, which is precisely the trap here.

**UNVERIFIED:** whether librsvg as bundled in sharp 0.34.5 honours a base64 `@font-face` in every case. Test option 1 before relying on it, or use option 2.

### The 2026 favicon set

The set consolidated. The minimal modern set is: `favicon.ico` (32x32, for legacy and for the browser tab in older clients), one `icon.svg` (scalable, and it can carry a dark-mode media query), one `apple-touch-icon.png` at 180x180, and a web manifest referencing 192x192 and 512x512 PNGs. That is five files, not the forty that older generators emit.

**UNVERIFIED:** the precise current recommendation from the well-known consolidation write-up; this reflects the shape the maintained tools now emit rather than a single quoted source.

```powershell
npx favicons-cli docs/images/logo.png -o docs/images/icons
# or drive the library directly from a script for exact control over the emitted set
npm i -D favicons
```

Given `sharp` is already present, generating the PNGs plus the `.ico` directly is roughly fifteen lines and avoids pulling a second duplicate sharp binary through `favicons`:

```js
// scripts/build-favicons.mjs  (.mjs: png-to-ico@3 is ESM-only, "type": "module")
import sharp from 'sharp';
import pngToIco from 'png-to-ico';
import { writeFile } from 'node:fs/promises';

for (const size of [180, 192, 512]) {
  await sharp(MASTER).resize(size, size, { fit: 'contain', background: { r: 0, g: 0, b: 0, alpha: 0 } })
    .png().toFile(`icons/icon-${size}.png`);
}
// descending order, see note below
const ico = await pngToIco([48, 32, 16].map((s) => `icons/ico-${s}.png`));
if (!(ico[0] === 0 && ico[1] === 0 && ico[2] === 1 && ico[3] === 0)) {
  throw new Error('not a valid ICO');   // see the silent-PNG trap below
}
await writeFile('icons/favicon.ico', ico);
```

Three things this guards against, each verified:

- **sharp writes a PNG when you ask it for an `.ico`, silently.** `sharp(...).toFile('trap.ico')` reports format `png`, writes the PNG magic bytes `89504e470d0a1a0a`, exits 0, and emits no warning. The file has no valid ICO header. This is precisely the mistake an agent iterating on a favicon script makes and does not catch, which is why the generator should assert the magic bytes and fail loudly.
- **`fit: 'contain'` is mandatory here**, because the logo viewBox is 250x210 rather than square.
- **`png-to-ico@3.0.2` is ESM-only** (`"type": "module"`). Writing the generator as `scripts/build-favicons.mjs` matches the existing `build-lucide-bundle.mjs` convention and sidesteps the interop question.

**On ICO size ordering:** RealFaviconGenerator's source carries a comment claiming ascending order corrupts the icon in Chrome and recommends `[48, 32, 16]`. Testing `png-to-ico` both ways showed it preserves whatever order it is given, with identical byte length and structurally valid output either way. The Chrome rendering claim itself is **UNVERIFIED**. Descending order costs nothing, so use it.

**Avoid `electron-icon-builder` entirely.** Beyond being four years stale, its chain is `jimp ^0.16.1` to `@jimp/core` to `phin ^2.9.1`, and `phin` carries GHSA-x565-32qp-m3vf with the fix in 3.7.1. The `^2.9.1` range sits **structurally below the patch**, so no override short of a forced resolution can fix it. `sharp-ico@0.1.5` does work with sharp 0.35.x despite its `"*"` pins, but it only writes to a file path and never returns a buffer, and an unbounded pin is a future landmine.

### Ad stills: one template, many artboards

The pattern people use in 2026 for a consistent set is a single HTML file driven by a data manifest, rendered in a loop. Artboards as sibling `<section>` elements, each sized exactly, each screenshotted by element:

```js
const ARTBOARDS = [
  { id: 'og',      w: 1200, h: 630  },
  { id: 'avatar',  w: 1024, h: 1024 },
  { id: 'banner',  w: 1500, h: 500  },
  { id: 'social',  w: 1280, h: 640  },  // GitHub repo social preview
  { id: 'ad-1',    w: 1600, h: 900  },
  { id: 'ad-2',    w: 1080, h: 1350 },  // portrait for social feeds

```

Composite a real app screenshot inside a CSS-drawn browser frame over a gradient plate. A browser frame is a `border-radius`, a title bar and three dots in CSS; it needs no asset and no third-party mockup service, and it stays on-brand automatically because it uses the same tokens as the app.

**Note on the project's own design rules:** the global instructions ban the status-pill-with-dot pattern outright, and require that repeated gradient or grid textures be visibly distinct per card. Seed each artboard's gradient from its `id` so no two ad stills carry the same texture.

Screenshot-beautifier services such as shots.so and screenshot.rocks are widely used, but they are hosted GUI tools rather than scriptable pipelines, so they do not fit an agent-driven build. **UNVERIFIED:** whether any of them currently offers a self-hostable or API path.

**On the CLI beautifiers.** Verified as alive: `appshots` 1.2.1 MIT, `storepix` 0.4.0 MIT, `devices.css` 0.2.0 MIT with a 390x830 iPhone screen, `carbon-now-cli` 2.1.0 MIT, `raycast/ray-so` MIT.

`appshots` is **disqualified for anything with headline text**, for the same reason the competitor's social script is. Its `src/core/framer.ts` renders titles as `<text font-family="...">` inside generated SVG strings piped through sharp, and the font stack is a hardcoded constant rather than an option:

Apple Design Resources, mockuphone's CC BY 3.0 attribution chain and similar asset packs carry redistribution conditions that were **not independently re-verified here**; read the license files directly before shipping marketing material that embeds third-party device art.

### The prerelease dist-tag question, answered from the npm CLI source

This was verified by reading `lib/commands/publish.js` on npm/cli main, not from a blog post:

```js
const isDefaultTag = this.npm.config.isDefault('tag') && !manifest.publishConfig?.tag
const isPreRelease = Boolean(semver.parse(manifest.version).prerelease.length)
if (isPreRelease && isDefaultTag) {
  throw new Error('You must specify a tag using --tag when publishing a prerelease version.')
}
```

So:

- npm does **not** infer a dist-tag from the version string. The `tag` config default is and remains `latest`.
- On npm 10 and older, publishing `1.2.0-alpha.11` untagged **silently moves `latest`**. That is the classic footgun.
- On npm 11.0.0 and newer, npm **hard errors** instead. Because Trusted Publishing requires npm 11.5.1+, any OIDC publish path has this guard rail automatically.
- Do **not** set a static `publishConfig.tag` of `alpha`, because it would then tag the eventual stable `1.2.0` as alpha too. Derive the tag from the version at publish time.

### The release workflow

```yaml
name: Release
on:
  push:
    tags: ['v*']
permissions:
  contents: read
jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      contents: write   # create the GitHub Release
      id-token: write   # required for npm OIDC trusted publishing
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: '24'          # Node 22 ships npm 10.9.8, below the 11.5.1 floor
          registry-url: 'https://registry.npmjs.org'
          package-manager-cache: false
      - run: npm ci
      - run: npm test
      - name: Derive dist-tag from version
        id: tag
        run: |
          VERSION=$(node -p "require('./package.json').version")
          TAG_VERSION="${GITHUB_REF_NAME#v}"
          if [ "$VERSION" != "$TAG_VERSION" ]; then
            echo "package.json is $VERSION but tag is $TAG_VERSION" >&2; exit 1
          fi
          PRE=$(node -p "(require('semver').parse('$VERSION').prerelease[0] || '')")
          if [ -n "$PRE" ]; then
            echo "dist_tag=$PRE"   >> "$GITHUB_OUTPUT"
            echo "prerelease=true" >> "$GITHUB_OUTPUT"
          else
            echo "dist_tag=latest"  >> "$GITHUB_OUTPUT"
            echo "prerelease=false" >> "$GITHUB_OUTPUT"
          fi
          echo "version=$VERSION" >> "$GITHUB_OUTPUT"
      - name: Publish to npm
        run: npm publish --tag "${{ steps.tag.outputs.dist_tag }}"
      - name: Extract this version's changelog section
        run: |
          awk -v v="${{ steps.tag.outputs.version }}" '
            $0 ~ "^## \\[" v "\\]" {f=1; next}
            f && /^## \[/ {exit}
            f {print}
          ' CHANGELOG.md > RELEASE_BODY.md
          test -s RELEASE_BODY.md || echo "See CHANGELOG.md" > RELEASE_BODY.md
      - name: Create GitHub Release
        uses: softprops/action-gh-release@v3
        with:
          tag_name: ${{ github.ref_name }}
          name: v${{ steps.tag.outputs.version }}
          body_path: RELEASE_BODY.md
          prerelease: ${{ steps.tag.outputs.prerelease }}
```

One-time setup: on npmjs.com, in the package settings for `myrlin-workbook`, add a Trusted Publisher with owner `therealarthur`, repo `myrlin-workbook`, workflow file `release.yml`. It must match exactly or publishing fails with a misleading **E404 Not Found** rather than an auth error.

`softprops/action-gh-release` is at **v3.0.2**, MIT, last pushed 2026-08-16. Its README notes that v2.6.2 is end of life because it runs deprecated Node 20.

GitHub protects you where npm does not: marking a release `prerelease: true` automatically excludes it from "Latest", because per the REST docs "Drafts and prereleases cannot be set as latest."

### Launch timing conventions

**Hacker News**, from https://news.ycombinator.com/showhn.html : "Show HN is for something you've made that other people can play with", and critically **"New features and upgrades ("Foo 1.3.1 is out") generally aren't substantive enough."** Also "Please don't ask friends to upvote or comment." Practical consequence: **do not Show HN an alpha bump.** You get one Show HN at 1.0 quality, roughly once a year.

**Product Hunt**, from https://www.producthunt.com/launch : "12:01 am Pacific Time is the best time to launch", so the convention still holds in 2026. "You cannot ask people directly to upvote your product. Instead, ask them to visit and comment."

**Lobsters**, from https://lobste.rs/about : invitation only, self-promotion should be "less than a quarter of one's stories and comments", and new members cannot submit links to previously unseen domains until 70 days in. Plan the invite well ahead of launch.

**Reddit: UNVERIFIED.** Every fetch path returned an anti-bot challenge. Read the live sidebars of r/programming, r/javascript and r/selfhosted manually before posting, and check the existing `reddit-launch-post.md` against them.

### README rendering, measured against the real GitHub Markdown API

Rather than trusting docs, the GFM API (`POST /markdown`, `mode: gfm`) was run against a test document. Because npm renders READMEs through that same API, one test answers both.

| Element | Result |
| --- | --- |
| `<picture>` with `prefers-color-scheme` | **Survives**, both URLs camo-proxied |
| `<details>` / `<summary>` | Survives |
| `> [!NOTE]` alerts | Renders as a styled alert div |
| Raw `<table>` HTML | Survives |
| `<video>` tag | Survives sanitization, but GitHub's docs only promise it in issue and PR comments. **Treat README video as unreliable** |
| SVG via `<img src="x.svg">` | Survives, camo-proxied |
| **Inline `<svg>` element** | **Stripped entirely** |
| **Relative image path** | **Left relative.** Breaks on npm |
| ` ```mermaid ` fence | Syntax-highlighted only; rendered client-side on github.com, so **not on npm** |

The dark and light image pattern, verbatim from https://github.blog/changelog/2022-05-19-specify-theme-context-for-images-in-markdown-beta/ :

```html
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="...dark.png">
  <img alt="Descriptive alt text" src="...light.png">
</picture>
```

**npm rendering rules**, verified from npm's own docs source: the README is rendered as GitHub Flavored Markdown via GitHub's API; it must be in the package root; and it "will only be updated on the package page when you publish a new version". So a README fix requires a version bump. Relative image paths resolve against npmjs.com and 404, so **use absolute `https://raw.githubusercontent.com/therealarthur/myrlin-workbook/main/...` URLs** for every image that must appear on npm.

Repository social preview: at least 640x320, **1280x640 for best display**, under 1 MB, PNG, JPG or GIF.

## 11. Production plan for the media set

### The harness

One new file, `test/media/capture.js`, built as a sibling of `test/browser/notion-shell.spec.js` so it inherits the safety properties that file already proved out: spawn the server on an ephemeral port, never touch 3456, seed deterministic fixtures with frozen timestamps, and drive Playwright at fixed viewports.

Shape:

```js
// Desktop: 1440x900. Phone: 390x844. deviceScaleFactor 1 for video, 2 for stills.
const ctx = await browser.newContext({ viewport: { width: 1440, height: 900 } });
const page = await ctx.newPage();
await page.goto(`http://127.0.0.1:${port}/`);
await page.screencast.start({ path: `raw/${clip}.webm`, size: { width: 1440, height: 900 }, quality: 90 });
await page.screencast.showActions({ cursor: 'pointer', position: 'bottom-right' });
await page.screencast.showChapter('Session discovery', { description: 'Every Claude and Codex session on disk' });
// ... scripted interaction ...
await page.screencast.stop();
await ctx.close();
```

Each clip is a named scene function so clips can be re-shot individually. Encode is a second pass over `raw/` using the ladder in area 4, which keeps capture and encode independently re-runnable.

**Critical constraint carried from the measurements:** screencast frames are 1x CSS pixels. Capture at 1440x900 and downscale to 1100px or 900px for the README, which supersamples and keeps text crisp. Use `page.screenshot({ ... })` with `deviceScaleFactor: 2` for every still.

## 12. Risks and gotchas

### Windows specific

- **`ffmpeg-static` on Windows is a gyan.dev GPL-3.0 build.** Fine for producing media, since output is not a derived work, but do not link against it and do not redistribute it inside the npm package.
- **VHS does not reliably record on Windows.** Issue 631 "Recording doesn't work on windows 11" is open, along with reports of freezes and blank frames. Run terminal captures on the Mac Mini over SSH.
- **asciinema has no Windows support at all**; the install docs list Linux, macOS, FreeBSD and OpenBSD only.
- **`gdigrab` will not give a true 60 fps** and captures screen regions rather than viewports. Avoid OS-level capture entirely.
- **Neither brand font is installed system-wide**, which silently breaks any non-browser SVG text renderer. See below.
- **Do not run a second workbook server on port 3456.** Per project memory, 3456 serves a different checkout under a scheduled task. The existing harness already refuses that port; keep that guard.

### Licensing

- **Remotion is source-available, not open source.** Free for a solo maintainer, but a 4+ person company needs a paid license. Keep it out of the published package's dependency tree so downstream consumers of this AGPL-3.0 package never inherit that obligation.
- **GSAP is free but not OSI**, with a competitor carve-out and Webflow's right to change terms.
- **FLUX.2 dev and klein 9B weights are non-commercial.** Only klein 4B is Apache-2.0.
- **Recraft free-plan images are owned by Recraft and are public.** Never generate brand assets there.
- **gifski is AGPL-3.0** and ships no prebuilt Windows binary. Skipped anyway.
- **Gemini's free tier trains on submitted content.** Use a paid key for brand work. All Gemini images carry a SynthID watermark.

### Size and rendering

- **A WebP without `-loop 0` plays once and stops.** It looks correct locally and broken on GitHub. Run the `webpinfo.js` check on every file before committing.
- **sharp resizing by height destroys an animation** because sharp stores frames as one tall filmstrip. Resize by width only.
- **Animated AVIF renders as a broken image on GitHub.** Do not use it.
- **Inline `<svg>` is stripped from READMEs.** Reference SVG through `<img>`.
- **Mermaid renders on github.com but not on npm.**
- **`<video>` in a README is unreliable.** GitHub's docs only promise it in issue and PR comments. Use the poster-image-linking-to-MP4 pattern.
- **Relative image paths break on npm.** Use absolute raw.githubusercontent URLs.
- **A README fix requires a version bump**, because npm only re-renders the README on publish.
- **WebP embedded externally: partly resolved.** A user in GitHub community discussion 171343 reported WebP from GitHub *asset* endpoints, the user-attachment style URLs, returning 404 when embedded on npm. That does **not** apply to repo files: MEASURED HERE, `raw.githubusercontent.com` serves the competitor's animated WebP as HTTP 200 with `Content-Type: image/webp`, and the `github.com/.../raw/...` path 302-redirects to it. So absolute `raw.githubusercontent.com` URLs are the safe form. Whether npmjs.com's own renderer then displays it is still **UNVERIFIED**, because npmjs.com blocks automated fetches. Mitigation: use raw.githubusercontent absolute URLs, and keep a static PNG hero as the first image so the npm page is never empty.
- **GIFs already in git history stay there forever.** The 13.5 MB currently committed will be paid by every clone even after conversion. Removing them from history requires a rewrite, which is likely not worth it; just stop adding new ones.

### Silent failures, the category that will actually bite

Every one of these exits 0 and produces a plausible-looking file. None of them raises an error. Collectively they are the biggest risk in this pipeline, because an agent iterating quickly will not notice any of them.

| Silent failure | Detection |
| --- | --- |
| sharp substitutes a fallback font for an uninstalled family | Render a known string and hash it against the same string in a deliberately bogus font; identical hashes mean substitution |
| `sharp(...).toFile('x.ico')` writes a **PNG** | Assert ICO magic bytes `00 00 01 00` |
| WebP without `-loop 0` plays once | `webpinfo.js` from area 4, assert `loop=0` |
| sharp resize by height flattens the animation filmstrip | Only ever resize by width; assert `pages` survived |
| ffmpeg picks `yuv444p` from PNG input | Assert `-pix_fmt yuv420p` is present in every MP4 command |
| Screenshot captures fallback glyphs before webfonts settle | `await page.evaluate(() => document.fonts.ready)` before every capture |
| `appshots --title` renders in Segoe UI regardless of intent | Do not use it for text |
| `git add` on a gitignored path does nothing | `git check-ignore -v <path>` before assuming a commit staged |

The general rule: **this pipeline should assert its outputs, not just produce them.** A verification pass over `docs/media/` that checks frame counts, loop flags, pixel formats and magic bytes is worth more than any of the individual tool choices.

### Agent-workflow specific

- **`page.screenshot()` at `deviceScaleFactor: 2` on a 1440x900 viewport produces a 2880x1800 PNG**, which exceeds the 2000px review limit. Always downscale before any agent reads a still.
- **Wall-clock animation engines desynchronize under frame-by-frame rendering.** Drive GSAP, Anime.js, Motion and Rough Notation from the frame number, never let them auto-play inside Remotion.
- **Do not trust MCP registry listings.** Verify the repo, license and last commit before adopting anything.
